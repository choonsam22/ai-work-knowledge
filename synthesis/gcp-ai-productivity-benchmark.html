1. 조사 방향을 다시 정의했다

세아제강 DX팀에 필요한 것은 “직원들이 AI로 이메일을 잘 썼다”는 사례가 아니다. 원가 압력이 큰 업종에서 반복적인 데이터 입력·검색·주문처리·영업판단을 어떻게 업무시스템과 연결해 줄였는지, 그리고 그 기반을 누가 어떻게 운영했는지가 핵심이다.

GCP 적합성

BigQuery, Vertex AI, Document AI, Gemini Enterprise, Cloud Run/Functions, GKE 등 현재 환경에서 재현 가능한가.

비부가가치 제거

메일·PDF 재입력, 자료 취합, 주문 확인, 상품 추천 준비처럼 사람의 판단가치를 거의 만들지 않는 시간이 줄었는가.

저마진 업종 유사성

자동차·산업재·FMCG·식품유통처럼 재고, 가격, 리드타임, 현금전환주기의 압력이 큰 업종인가.

결과 검증 가능성

실제 운영수치, 전후시간, 처리량, 비용 또는 매출 관련 지표가 공개됐는가. 목표치는 별도로 표시했는가.

한 문장 결론: 세아제강은 범용 챗봇을 넓게 배포하기보다, ERP·CRM·문서·현장 데이터를 BigQuery/GCS에 연결하고, 좁은 업무 Agent를 사람 승인과 함께 운영하는 방향이 맞다.

01

Renault Group — AI보다 먼저 산업데이터의 공통 언어를 만들다

40개 공장으로 확장 가능한 Industrial Data Management 4.0

방향성·데이터 기반 · A+B
4,900+ 설비2021년 GCP 연결 · 측정치
10억 메시지/일GCP 수집량 · 측정치
생산비용 50%↓특정 비효율 클러스터 수정효과 · 플랫폼 전체 아님

업무문제

Renault에는 예지보전, 추적성, 설비데이터 수집, AI 프로젝트가 공장별로 흩어져 있었다. 문제는 AI 모델 부족이 아니라 서로 다른 설비·공장·업무가 데이터를 다른 방식으로 만들고 있어, 매번 별도 연결과 전처리를 해야 한다는 점이었다.

구현구조

2019년 IDM 4.0을 시작해 공장 설비 데이터를 표준모델로 수집하고 GCP에 연결했다. Pub/Sub와 Dataflow가 스트리밍·배치 수집을 담당하고, BigQuery가 표준 산업데이터를 저장·분석한다. 2021년 기준 4,900개 이상 설비에서 하루 10억 메시지를 처리했다. Renault 공식 자료는 이후 산업설비 70% 이상 연결, 2019년 이후 300개 경보 탐지와 생산중단 회피를 밝혔다.

성과를 정확히 읽기

  • 초기 GCP 이전 시험에서 저장비용 50% 이상 감소가 확인됐다.
  • Cloud Storage를 불필요하게 매우 자주 조회하던 Spark 설정을 고쳐 관련 호출을 100분의 1로 줄였고, 해당 운영구간의 생산비용을 50% 낮췄다.
  • 이 50%는 전체 제조원가나 전체 클라우드비용 감소가 아니다.
  • 300개 경보와 생산중단 회피는 Renault 공식 자료지만, 금액효과와 오탐률은 공개되지 않았다.

왜 중요한가

AI 과제를 먼저 나열하지 않고 데이터 수집·표준화·비용관측을 공통제품으로 만든 것이 핵심이다. 플랫폼팀이 데이터 계약과 비용을 관리하고 현업이 그 위에서 분석·AI를 만드는 구조다.

근거 공백: 2021년 Google Cloud 수치와 이후 Renault 공식 수치의 기준시점이 다르다. “생산중단 회피”의 재무효과는 공개되지 않았으며 인과관계도 독립 검증되지 않았다.
세아 적용: 전사 데이터레이크부터 시작하지 않는다. PM53 또는 한 관리업무를 골라 설비/ERP 원천 1~2개 → 공통 이벤트·마스터 정의 → BigQuery 표준 테이블 → 1개 분석/Agent까지 하나의 데이터 제품으로 완성한다. 데이터 수집 성공률, 지연시간, 스키마 오류, 쿼리·저장비용을 DX팀의 제품 KPI로 둔다.

FibroGen — 회계 AP의 PDF Invoice 입력을 3개월 안에 자동화

거대한 재무 AI가 아니라 2인 팀의 반복 입력을 Document AI와 SAP로 연결

회계·재무 · B
1,000건/월공급사 Invoice 처리량 · 기준선
500시간/인·년기존 입력시간 · 계산치
$150/월 · ROI 40배운영비와 ROI 모두 추정치

업무문제

2명으로 구성된 AP팀은 매월 약 1,000개의 Invoice PDF를 이메일에서 내려받아 공유폴더에 저장하고, 건당 평균 5분씩 SAP에 재입력했다. 1인당 연 약 500시간, 전체 근무시간의 약 25%가 단순 입력에 쓰였다.

구현구조

AP 담당자가 PDF를 GCS 버킷에 올리면 Cloud Functions가 Document AI Invoice Parser를 호출한다. 추출 결과는 JSON으로 전달되고 SAP Cloud Integration에서 신용메모 구분 등 비즈니스 규칙을 적용한 뒤 SAP R/4에 입력한다. 신뢰도가 임계치보다 낮으면 AP 담당자의 검토로 보낸다. 설계부터 운영 배포까지 3개월 미만이 걸렸다.

성과를 정확히 읽기

  • 월 $150 운영비, AP 용량 25% 확보, ROI 40배는 추정치다.
  • 운영 배포 사실은 확인되지만 실제 필드 정확도·예외율·월간 절감시간은 공개되지 않았다.
  • 초기에는 이메일→GCS 업로드가 수동이며, 완전한 Straight-through Processing이 아니다.
  • FibroGen 직원이 Google Cloud 글의 공동 저자로 참여해 구조는 신뢰할 만하지만 독립 검증은 아니다.

성공조건

AI 추출과 회계 규칙을 분리했다. 금액·세금·거래처·PO 일치 여부는 결정론적 규칙으로 검증하고, AI는 문서에서 후보값을 읽는 역할만 맡는다.

근거 공백: 제목의 “40x ROI”는 실현 ROI가 아니라 예상치다. 운영 후 실제 정확도와 예외처리 비용이 공개되지 않아 세아 파일럿에서 반드시 직접 측정해야 한다.
세아 적용: 국내외 모든 Invoice를 한 번에 다루지 말고, 양식 변동이 적고 월 처리량이 많은 1개 법인·1개 거래유형·핵심필드 10~20개로 시작한다. KPI는 필드정확도, PO/계약 자동대조율, 예외율, 재작업시간, 건당 GCP비용이다. 지급·세무판단은 끝까지 사람이 승인한다.

Danfoss — 이메일 주문·견적을 ERP 행동으로 바꾸는 Agent

산업재 제조사의 주문관리, 고객응대, 현금전환주기를 동시에 겨냥

영업·주문 사무 · B
의사결정 80%+Agent가 처리 · 기업 자체 추정
약 5분/주문평균 절감 · 기업 자체 추정
처리시간 50%↓Google Cloud 고객사례 보고

업무문제

대형 고객은 EDI 등 시스템 연계가 가능했지만, 복잡한 주문을 보내는 고객은 이메일 본문·표·PDF·이미지·스프레드시트로 주문과 견적을 요청했다. 직원은 최대 5개 시스템을 오가며 품번, 가격, 수량, 예외를 확인했고 평균 응답이 약 42시간 걸렸다.

구현구조

Danfoss는 범용 LLM을 자체 구축하지 않고 Google Cloud Marketplace의 Go Autonomous 수직형 플랫폼을 선택했다. 전문 AI 모델과 Agent가 이메일 요청을 해석하고 ERP·CRM 커넥터를 호출한다. GKE가 컨테이너형 서비스를 운영한다. 가격예외 등 복잡한 거래는 사람에게 넘기며, 향후 BigQuery를 연결해 Agent가 더 많은 예외를 판단하도록 계획한다.

성과를 정확히 읽기

  • 현재 80% 이상의 거래 의사결정을 Agent가 수행하고 수동처리 주문은 감소 중이라고 회사가 추정했다.
  • 주문당 평균 약 5분 절감, 전체 처리시간 50% 감소가 보고됐다.
  • 42시간→1분 미만과 수백만 유로 절감은 향후 목표·전망이다.
  • GCP를 쓰지만 AI 모델 자체는 Go Autonomous의 독점 기술이다. 세아가 동일 구조를 직접 개발한 사례가 아니다.

핵심 교훈

메일을 요약하는 데서 멈추지 않고 ERP 행동으로 이어져야 가치가 생긴다. 동시에 범용 모델보다 품번·가격불일치·첨부문서·사내 주문규칙을 이해하는 수직형 업무모델이 중요하다.

근거 공백: 80%의 정확한 분모, 오류·취소·재주문율, 고객별 범위가 공개되지 않았다. 42시간→실시간은 아직 전체 실측치가 아니다.
세아 적용: 영업대표를 대신하는 Agent가 아니라 공용 주문메일함의 접수 Agent부터 만든다. 본문·첨부에서 고객/품번/규격/수량/납기요청을 추출하고 ERP·재고·가격표와 대조한 뒤 “자동확정 가능 / 정보부족 / 가격예외 / 사람검토”로 분류한다. 첫 단계에서는 ERP 쓰기 없이 초안과 검증결과만 제공한다.

Wipro Enterprises — Excel 영업을 BigQuery 기반 추천영업으로 전환

IT서비스 회사가 아닌 Wipro Consumer Care의 저마진 FMCG 사례

영업·수익성 · B
판매 품목수 15~20%↑거래처당 Product Lines · 실측/기업발표
신규 매장 15,000개인도 1개 주 · 확보 성과
재구매 30~40%신규 확보 매장 · 기업발표

업무문제

수백만 개의 소매점과 많은 SKU를 다루면서 영업사원은 기억과 경험에 의존해 상품을 추천했다. 이직률이 높은 환경에서 신입은 제품지식을 익힐 시간이 부족했다. ERP와 유통관리시스템의 데이터는 분리돼 있었고, 보고는 Excel 추출에 의존해 실시간 분석이 어려웠다.

구현구조

2년에 걸쳐 BigQuery에 판매·거래처·제품 데이터를 통합하고, Vertex AI가 과거판매, 지역 구매패턴, 거래처 구매력을 분석해 매장별 “필수 진열 목록”을 추천하게 했다. Google Maps Platform은 미개척 매장을 찾고 경로를 만들었다. BigQuery 기반 Sales Control Tower에서 지역관리자가 추천 부진 지역을 확인하고 모델 조정 또는 판매 인센티브를 결정한다.

성과를 정확히 읽기

  • 거래처당 판매 품목수가 15~20% 증가했다. 이는 매출액·영업이익 증가율과 동일하지 않다.
  • 한 개 주에서 신규 매장 15,000개를 찾았고, 신규 매장의 재구매율은 30~40%로 보고됐다.
  • 추천이 영업사원의 기억을 대체했지만 모델 운영은 외부 전문파트너가 지속적으로 조정한다.
  • 자연어 브랜드 분석과 생성AI 설명 기능은 향후 구상이며 실적에 포함하면 안 된다.

핵심 교훈

영업 AI의 출발은 제안서 문장생성이 아니라 거래처·품목·지역·판매이력의 통합이다. 추천 결과를 관리자가 Control Tower에서 검증하고 현업의 결과가 다시 모델에 들어가는 폐쇄루프가 핵심이다.

근거 공백: 모델 추천을 따르지 않은 대조군, 할인·프로모션 영향, 매출총이익 변화가 공개되지 않았다. 15~20%를 AI의 순수 인과효과로 단정할 수 없다.
세아 적용: 고객별 “다음 제품” 추천보다 먼저 고객×품목×규격×지역×가격×납기×마진의 영업 데이터마트를 만든다. 초기 모델은 이탈고객, 교차판매 후보, 장기미구매 품목, 견적후 미수주를 우선순위화한다. KPI는 추천채택률, 견적전환율, 재구매율, 추가 매출총이익이며 단순 매출액만 보지 않는다.

업무문제

AI 활용요청과 Agent 후보가 중앙 개발팀의 처리능력보다 빠르게 늘었다. 유용한 답을 만들려면 SAP S/4, ServiceNow, Concur, Jira, Confluence, GitLab 등 여러 시스템의 업무맥락을 권한에 맞게 연결해야 했지만, 매번 커스텀 커넥터를 만드는 것은 병목이었다.

구현·운영구조

Gemini Enterprise의 사전 구축 커넥터로 내부 데이터를 연결하고, 중앙팀은 후보 업무를 선별한다. 기술자는 ADK로 전문 Agent를 만들고, 향후 비개발 현업도 No-code Agent Designer로 워크플로를 만든다. 한 플랫폼의 Agent Gallery에서 난립을 줄이는 방향이다. Tyson Foods와는 A2A 프로토콜을 이용해 내부 메모리·도구·로직을 노출하지 않고 상품검색·판매추적 Agent 간 통신을 시험했다.

성과를 정확히 읽기

  • 약 7,000명이 Gemini 기반 도구를 사용하고, 통합 도구를 통한 의사결정·콘텐츠 작성에서 월 2만시간 이상 절감을 보고했다.
  • 이 수치는 특정 Agent 하나의 성과가 아니라 Google Workspace 통합도구 전반의 합산치다.
  • ServiceNow 티켓 자동생성, 현업 No-code Agent 확대는 아직 계획·진행단계다.
  • Tyson과의 A2A는 Pilot이며 생산확대가 계획된 상태다.

핵심 교훈

DX팀은 모든 Agent의 개발자가 아니라 수요 심사자·공통 연결 제공자·등록부 운영자·성과 감사자가 돼야 한다. 현업 제작을 허용하되 중앙 플랫폼에서 오너, 권한, 비용, 버전, 이용률, 폐기일을 관리한다.

근거 공백: 월 2만시간의 산식, 업무별 분해, 품질·오류지표가 공개되지 않았다. No-code Agent의 실제 운영규모와 폐기율도 아직 확인할 수 없다.
세아 적용: “사내 Agent 100개”를 목표로 삼지 않는다. DX팀이 Agent 등록부를 만들고, 업무오너·데이터소스·권한·사람승인·월비용·KPI·최종사용일을 필수 필드로 관리한다. 첫 공통 커넥터는 Google Drive/Shared Drive, BigQuery, ERP 조회 API, 사내 문의시스템 순으로 만든다. 60일 미사용 또는 KPI 미달 Agent는 폐기한다.
